## [Unreleased]

## [0.22.1] - 2026-10-23

### Fixed

- omp `judge` role assigned to a jev model never loaded (`model role "judge" = "…" unavailable`, gate fell back to the session model): the role selector was resolved through `ctx.models.resolve`, which searches chat models only, so no judge-kind model ever resolved (and the "judge model pi-verdict cannot call" skip never ran). Role selectors now fall back to a `provider/id` registry lookup with a configured-auth check, and omp's OpenRouter-hosted jev judge models (`openrouter/typesafe/jev-*`, api `openrouter-decisions`) are callable: `completeForClassifier` posts to the openrouter decisions endpoint with the model's own id as wire model (`streamDecisions` gained an optional `wire` argument). Other judge-kind models (native judgment runner, `typesafe/jev-*` direct) are still skipped with one warning, and on the `verdict-fallback` / `explain-gate` roles count as unavailable ([CL-2](docs/adjudication-rules.md#cl-2-classifier-model-resolution)).

## [0.22.0] - 2026-10-19

### Added

- **Gate briefing** ([GR-7](docs/adjudication-rules.md#gr-7-gate-briefing)): every agent turn the `before_agent_start` hook appends a `## Permission gate (pi-verdict)` section to the system prompt (pi string and omp section list both supported) that names the approval mode, lists the effective `deny` and `ask` danger rules, the non-`allow` path tiers, the `denyPaths` count (never the paths, PP-6) and the `.omp` gate, and tells the agent not to retry or rephrase a blocked call but to request a `verdict_grant` (subagents report the need instead). Omitted when the mode is `off` or for a subagent while `subagentGate` is `off`; no config switch, and it holds no per-session data besides mode and rules so the prompt stays cacheable.

### Changed

- **BREAKING**: the approval modes are renamed — `default` → `auto`, `yolo` → `unattended`, `noAutoDeny` → `supervised` (`off` is unchanged; `/automode` and `--verdict-mode` take `auto|unattended|supervised|off`, and the cycle shortcut order is `auto → unattended → supervised → off → auto`) — and so are the derived config and session keys: `defaultDenyThreshold` → `autoDenyThreshold`, `defaultAllowThreshold` → `autoAllowThreshold`, `yoloDenyThreshold` → `unattendedDenyThreshold`, `noAutoDenyAllowThreshold` → `supervisedAllowThreshold`, `yoloDenyPaths` → `unattendedDenyPaths`, `yoloOmpDir` → `unattendedOmpDir` ([MD-1](docs/adjudication-rules.md#md-1-modes-and-verdict-sets), [MD-6](docs/adjudication-rules.md#md-6-setting-a-mode)). A former mode value or key in a config or session override file is reported at start-up (`mode: "yolo" renamed to "unattended" — ignored`, `yoloOmpDir: renamed to unattendedOmpDir — key ignored`) and ignored, never mapped, so the mode falls back to `auto`, which is stricter than `unattended` and `supervised`; a former mode name given to `--verdict-mode` or `/automode` warns `renamed to <new>` and changes nothing. Migration: edit `pi-verdict.json` and any per-session override files by hand. The block tag `yolo-retry` is now `unattended-retry`, the reason suffixes read ` (unattended: no human can confirm this — …)` and ` (supervised: this would have been denied — your call)`, the audit `mode` field and the cascade trigger `yolo-ask` carry the new names (`unattended-ask`), and the glossary term "yolo-ask slip" is now "unattended-ask slip" ([PR-2](docs/adjudication-rules.md#pr-2-block-reason)).
- Mode chips: the footer shows `🛡 AUTO`/`auto`, `🌙 UNATTENDED`, `👁 SUPERVISED` and `⚠ AUTO OFF · ungated` (compact style `🛡 auto`, `🌙 unattended`, `👁 supervised`, `⚠ auto off · ungated`, replacing the `●`/`○` bullets; Nerd Font style uses `\uF186` and `\uF06E` for the moon and eye), and the prompt status-bar chip shows `🛡 AUTO`, `🌙 UNATT`, `👁 SUPV` and `⚠ OFF · ungated`.

## [0.21.1] - 2026-10-17

### Changed

- **Agent guidance for built-in rules**: the `verdict_settings` and `verdict_grant` tool descriptions and their `promptGuidelines` now tell the agent to check a built-in rule's current action with `verdict_settings` `get` (key `dangerRules` or `pathRules`) before saying it blocks an operation, and to request a `verdict_grant` listing the rule ids in `rules` (or protected paths in `paths`) instead of refusing or asking the user to run the step. Text only; gate behavior, `GRANT_BLOCK_HINT` and block reasons are unchanged.

## [0.21.0] - 2026-10-17

### Added

- **Configurable built-in rules** ([RL-5](docs/adjudication-rules.md#rl-5-danger-rules), [RL-6](docs/adjudication-rules.md#rl-6-builtindenyfloor), [PG-3](docs/adjudication-rules.md#pg-3-s0-secrets) to [PG-5](docs/adjudication-rules.md#pg-5-writes), [CF-4](docs/adjudication-rules.md#cf-4-merge-semantics) to [CF-6](docs/adjudication-rules.md#cf-6-invalid-values)): the built-in deny floor is now called *built-in rules* and every one of them carries a rule action — `deny`, `ask` or `allow` (`allow` passes no judgment: the call goes to the classifier, never a mechanical allow). New config key `dangerRules` (object keyed by danger-rule id: an action string changes a built-in, `false` removes it, `{pattern, action?, reason?, flags?}` adds a custom rule; defaults `deny`, reason `custom danger rule`, case-insensitive) and `pathRules` (path tier id → action; tiers `s0-secret`, `s1-system-read`, `s1-system-write`, `s2-user-rc-write`, `s3-git-meta-write` keep their old defaults). Both merge per id across global, trusted project and session scope, are settable through `verdict_settings` (`null` drops an id at a scope) and editable in `/verdict` on a new `danger rules & path tiers` page (←/→ cycles the action). A built-in `ask` opens the ask dialog with a UI (no Explain for path tiers, PP-9), is a grantable deny headless and in `yolo`, and is beaten by a user `allow` regex; when several danger rules match the strongest action wins and the reason lists every hit. Invalid entries are skipped with a warning. `builtinDenyFloor: false` now means every built-in rule acts as `allow`; custom danger rules stay active.
- **Grants can lift built-in rules** ([GR-1](docs/adjudication-rules.md#gr-1-request-tool), [GR-5](docs/adjudication-rules.md#gr-5-coverage-check)): `verdict_grant` `request` takes `rules` (at most 20 danger-rule ids, unknown ids rejected); a path grant's access entry also covers the built-in path-tier hits at that path. The coverage check now runs for built-in denies and asks too, and a block caused by a built-in rule carries the grant hint. Stored grants without `rules` still load. The classifier prompt lists a grant's rule ids and the grant dialog, `list` and `/grants` show them.
- **Inherited value on `inherit` rows**: in the `/automode` approval panel and the `/verdict` rules menu, a row that shows `inherit` (including a pending, not yet confirmed `inherit`) now carries a right-aligned `<value> · <source>` column (e.g. `ask · global`, `off · default`) with what `inherit` resolves to from the lower scopes (session → trusted local → global → default); the `mode` row shows it before the shortcut (`yolo · global  ctrl+shift+y`). It covers the choice and percent rows, the `gateOmpDir`/`footer`/`modeStatus`/`grantStatus` switches and the built-in rules page (danger rules and path tiers); global scope never shows it, and cycling to any other value hides it. The live effective value stays in the `Effective:` description line.
- **Remembered approval** ([PR-9](docs/adjudication-rules.md#pr-9-remembered-approval)): every ask dialog except the permission-grant dialog gains a second row "Yes, and don't ask again this session". The Yes is kept in memory for the exact call (ask origin, tool name, input, cwd) and the identical call is then allowed right after the rule layer, without a classifier call or dialog, in every approval mode including `yolo`; a rule-layer deny is overridden only in `noAutoDeny`. Not audited; the footer shows the count (`👤 n`); `/automode forget` and the `/automode` panel (`f`) clear it; `session_start` resets it. The permission-grant dialog and the plain confirm fallback have no such row.

### Changed

- **BREAKING**: a user `deny` regex is now evaluated before the built-in rules ([RL-2](docs/adjudication-rules.md#rl-2-evaluation-order) step 1), so a call matching both reports the user-deny reason.
- **BREAKING**: path-tier block reasons are prefixed `tier <id>: ` (e.g. `tier s0-secret: S0 secrets/credential path: …`) so the agent can name the tier in a permission grant; block text from built-in rules ends with the grant hint, and in `yolo` a gate whose action is `allow` (`yoloDenyPaths`/`yoloOmpDir`) still refuses a call with built-in rule hits underneath.
- **BREAKING**: a permission grant can now lift a built-in rule deny (previously "a grant never overrides the built-in floor"); the audit record of such an allow has source `protected-path` and reason `permission grant <ids> covers this gated access` (was `… covers this protected-path access`).
- `rm-recursive` is now path-scoped ([RL-5](docs/adjudication-rules.md#rl-5-danger-rules)): it hits only when some `rm` operand resolves outside the workspace (session cwd) and the temp directory (`os.tmpdir()`, plus `/tmp` on non-Windows). When every operand of every matched `rm` segment lies strictly inside one of them, the rule makes no judgment and the call continues to user rules and the classifier (never a mechanical allow), at whatever action the rule is configured. Unresolvable operands (variables, command substitution, brace expansion, `~user`, relative operands after `cd`/`pushd`/`popd`, no operands as in `xargs rm -rf`, unbalanced quotes), the workspace or temp directory itself, a filesystem-root or home-directory cwd, and commands past `BASH_MAX_MATCH_LEN` still hit. `rm-root` is unchanged. No config key; the waiver is tied to the shipped rule.
- The settings menus (`/automode`, `/verdict`, root-rule menu) keep a constant height while the selection moves between rows, a value changes, a confirmation arms or the scope is switched with Tab: the description area reserves the line count of the tallest description any selectable row on the current page can show at any scope (every choice value, percent `off`/`N%`/`inherit` text, the worst-case precedence and untrusted-project warnings via the optional `MenuRow.maxInfo`, and the `press enter to apply` / `press enter again to confirm` / `press d again to remove` warnings), padded with blank lines below the description so the hint line stays on a fixed row. Height still changes on page change and terminal resize.

## [0.20.0] - 2026-10-16

### Added

- **Settings tool** `verdict_settings` ([ST-1](docs/adjudication-rules.md#st-1-actions-and-keys) to [ST-5](docs/adjudication-rules.md#st-5-writes)): an agent-callable tool, registered on pi and omp, with actions `get`, `set`, `unset`, `add` and `remove` over every config key except `_hint` at `global`, `local` or `session` scope (session takes the approval keys, `gateOmpDir`, `footer`, `modeStatus`, `rootRule` and list additions; `toggleShortcut` is global only; `mode: "off"` is session only). `get` returns the effective value, its source and the stored value per scope, and works without a UI; `denyPaths` is reduced to `{redacted: true, count}` and `denyPaths` `add`/`remove` give no membership signal before the dialog, so no protected path reaches the agent ([PP-6](docs/adjudication-rules.md#pp-6-plaintext-confinement)). Every change opens a confirmation dialog in every approval mode (including `yolo`) showing scope, key, action, before/after and the agent's `reason`; nothing is written unless the user approves, and a decline is a normal tool result. Values are validated like the config loader before the dialog, writes reuse `writeScoped` / `setSessionRuleAdditions` (a first `local` list change starts from a copy of the global list; an untrusted project is saved but not applied), and calls from subagents are refused, as are changes with no UI.
- **Permission grants** ([GR-1](docs/adjudication-rules.md#gr-1-request-tool) to [GR-6](docs/adjudication-rules.md#gr-6-lifetime-revocation-and-visibility), [RL-9](docs/adjudication-rules.md#rl-9-grant-tool)): the agent-callable tool `verdict_grant` (`request`, `release`, `list`; mechanical allow in the rule layer) asks for a session-long, natural-language authorization, optionally with protected-path access entries (`{path, access: read|write|full}`). The user approves through a new dialog (I approve / I reject / ask for clarification or revision; no Explain…), or, in `yolo`, the judge classifier and a configured `classifierFallbackModel` must both allow. Active grants (at most 20, ids `G<n>` never reused) are part of the user policy block of every classifier and fallback prompt and are authoritative within their literal scope; protected-path entries are sent only to the grant coverage check, which runs before a `denyPaths` or `.omp` gate ask (and before the yolo outcome): every touched protected path must lie under a grant entry with a fitting access level, then the judge and fallback must both allow, otherwise the ask stands (the exception to [PP-6](docs/adjudication-rules.md#pp-6-plaintext-confinement); uncovered calls never reach a model; headless works too). Grants persist in the session file (`grants`), are listed and revoked with `/grants [list|revoke <id>|revoke all]` (a revocation messages the agent), and show in the footer (`\uF084 n` full, `🔑 n` compact) and, on omp, in the prompt status bar (`grantStatus`, default `true`, session scope; [CF-5](docs/adjudication-rules.md#cf-5-session-scope)). With no grants nothing renders.

### Changed

- The rule layer allows calls to `verdict_settings` mechanically ([RL-8](docs/adjudication-rules.md#rl-8-settings-tool), [RL-2](docs/adjudication-rules.md#rl-2-evaluation-order) step 6): no classifier call, no user-regex, `.omp` gate or `denyPaths` check (the tool has no rule target), silent per PR-3; the tool's own confirmation dialog is the human gate.
- Block reasons of tags `classifier`, `yolo-retry` and `user-declined` now end with ` If this action is required, request a permission grant with verdict_grant (describe the exact operation and scope).` ([PR-2](docs/adjudication-rules.md#pr-2-block-reason), [GR-6](docs/adjudication-rules.md#gr-6-lifetime-revocation-and-visibility)); rule, fail-closed, protected-path and subagent blocks are unchanged because a grant cannot lift them. The classifier system prompt's user policy block (`userRulesHint`, now `classifierPolicy` + `trustedPolicyBlock`) gains the active grants after the classification rules; output without grants is byte-identical.
- `/verdict` gains a `grantStatus` switch row (default on, session-scopable), so the settings menu has one more row and the roles row moves down by one.
- All remaining Chinese text (code comments in `extensions/pi-verdict.ts`, test comments and fixture strings in `tests/pi-verdict.test.ts`, older `CHANGELOG.md` entries, and the `research/` notes and sims) translated to English; no runtime behavior changed. The `research/rule-engine-sim/measure.ts` end marker was updated to the translated `// Rule layer: file path sensitivity` heading.

## [0.19.0] - 2026-10-12

### Added

- **Root rule** and `/automode-setup [global|local|session]`: one free-text baseline policy for the classifier, stored under the new config key `rootRule` (`{text, strictness: "relaxed"|"balanced"|"strict", history, codebase, clarifications}`; default `null`; valid at global, local and session scope, where the highest scope that sets it wins as a whole object with no field merge; invalid fields are skipped with the usual load warning, [RR-1](docs/adjudication-rules.md#rr-1-storage-and-resolution)). The classifier prompt places it first inside the user-rules block (`Root rule (the project's baseline policy):`), with `rules` listed after it as `Classification rules (applied on top of the root rule …)` so a classification rule wins on conflict; without a root rule the prompt is byte-identical to before, the jev slice carries it, and the fallback classifier receives it too ([RR-2](docs/adjudication-rules.md#rr-2-composition), `userRulesHint`, `ClassifierPolicy`). `/automode-setup` opens a settings menu with the generator inputs (`strictness`, `history`, `codebase`, `clarifications`) and `g` / `generate`, an editor for the text and a per-scope remove; the `/automode` panel gets a `▸ root rule setup…` row (`r`). The session model drafts the policy from the current session branch (last 20 user lines and 100 tool-call lines, never tool output) and a deterministic project snapshot (`collectProjectContext`: top-level listing, docs, manifests, up to 5 CI workflows and git remotes with userinfo removed; S0 credential paths and `denyPaths` files are skipped and never named, PP-6), through the same generate → critic → feedback loop as `/rule` (up to 3 attempts, 4000-character limit, `generateRootRuleReviewed`); a preview always precedes saving, with edit and regenerate-with-feedback options ([RR-3](docs/adjudication-rules.md#rr-3-generator-inputs), [RR-4](docs/adjudication-rules.md#rr-4-loop-and-review)). Clarifications are persisted generator inputs and are never sent to the classifier. `anchorDenyPaths` is now exported.
- `/verdict` row `custom roles` (omp only, hidden on real pi, global scope only): adds or removes the `modelTags` entries `verdict-fallback` ("VERDICT FALLBACK") and `explain-gate` ("EXPLAIN GATE") in omp's `<agentDir>/config.yml` (`config.yaml` if that is the existing file), so both custom roles are listed in `/model` → Roles before they are assigned (omp lists a custom role only when assigned or tagged; extensions cannot register tags through omp's settings registry). The row is an `off`/`on` choice with `confirm`: `←/→` marks the new value as pending (warning color, the info line says what will be written) and `enter` applies it; moving away or `Esc` drops it. The write keeps every other key and tag (an existing entry for our key is left as-is; an emptied `modelTags` is dropped; `modelRoles` assignments are never touched), writes atomically with omp's own YAML serialization (comments in `config.yml` are not preserved) and calls `reloadFromDisk()` so `/model` updates without a restart. An unreadable `config.yml` (invalid YAML, non-mapping top level or `modelTags`) shows the row as `unreadable`, is reported in a warning notification and left untouched. New exports: `VERDICT_ROLE_TAGS`, `ompMainConfigPath`, `readOmpConfig`, `verdictRoleTagsPresent`, `withVerdictRoleTags`, `writeOmpConfig`.
- Reusable settings menu `buildSettingsMenu` (`MenuController`, `MenuRow`, `MenuScope` exported) behind `/automode` and `/verdict`: title border with a scope badge in the top-right (`⟨ session ⟩ tab ⇥`, `⟨ local · untrusted ⟩` in the warning color) cycled with `Tab` / `Shift+Tab` through global · local · session, section separators, `‹ value ›` chevrons on the selected multi-value row switched with `←/→` (`enter` steps to the next value with wrap-around), a 10-cell bar on percent rows (`←/→` ±5, `-`/`+` ±1, `x` off, `i` inherit; left of `0%` is `off`, then `inherit`), a per-row description under the list (value meaning, `Effective: <value> (<source>)`, and a `<source> sets this too and wins over <scope>` warning when a higher-precedence scope overrides the edited one) and list pages with inline add / edit (`enter`), `d` twice to remove and `←`/`esc` to go back. Every change is written immediately.
- `gateOmpDir` and `footer` are session-scopable (`SESSION_KEYS`, `SessionKey`): `/verdict session` writes them to the per-session overrides file; precedence is session > local > global > default. A session `gateOmpDir` that is not a boolean (or a `footer` outside `full|compact|off`) is skipped with a warning and the gate stays on. A config-file `gateOmpDir` that is not a boolean now also warns (it already kept the gate on).
- `modeStatus` config key (default `true`; session > local > global, editable from `/verdict` as the `mode in status bar` switch): controls the approval-mode chip (`🛡 AUTO` / `🛡 YOLO` / `🛡 NO-AUTODENY` / `🛡 OFF · ungated`, status key `verdict-mode`) in the prompt status bar — omp's status line `status` segment. The chip is now published with the footer on as well on omp (the footer is a below-editor widget there); on pi it stays hidden while the footer is on (the footer sits in that same bar and already shows the mode) and shown with `footer: "off"`. `modeStatus: false` hides it everywhere; a non-boolean value warns and counts as `true`.

## [0.18.0] - 2026-10-08

### Added
- `/rule [description]` command: the session model (thinking off) turns a natural-language description (plus the recent user messages and tool calls) into exactly one rule of kind `allow` / `deny` (regex), `denyPaths`, `tools` or `rules` (free-text classifier rule). The preview dialog shows the kind, value, rationale and — for regex, `denyPaths` and `tools` rules — which of the last 50 tool calls of this session the rule would match (`rules` entries cannot be checked); `tools` entries naming a path/command tool and invalid regexes are flagged and cannot be saved. Save targets: session only, project (`.omp|.pi/pi-verdict.json`; first add offers a copy of the global list, same as `/verdict`) or global (`<agentDir>/config/pi-verdict.json`); the value can be edited or amended with free-text feedback first. Session rules are stored under a new `ruleAdditions` key of the per-session overrides file and are **appended** to the effective user + project lists on every rules reload (restored on resume, never replacing a list; not applied when the user config failed to load). No protected-path plaintext is sent to the model (ADR-0002). Interactive UI and a session model are required.
- `/rule` generate → evaluate → correct loop: each candidate is checked before it reaches the preview, up to `RULE_MAX_ATTEMPTS = 3` attempts with every failure fed back to the next attempt as `<feedback>` plus the `<latest_candidate>`. Checks, in order: unparseable model output and `validateRule` errors; for `allow` / `tools` candidates `evaluateRuleOnHistory` re-runs each matching recent call through `classifyByRules` with the candidate appended, and a rule whose every match is still stopped by an earlier layer (built-in floor, user `deny`, the forced `.omp` gate, `denyPaths`) is rejected with the layer's reason (never `Verdict.detail`, ADR-0002); then one extra session-model critic call (`critiqueRule`, `ok` | `revise`) judges fit against the request, breadth against the non-matching recent calls and layer shadowing. A rule matching none of the recent calls is not a failure, the preview just warns. A transport error is not retried; an unavailable critic accepts the candidate marked `review unavailable`; after the last attempt the final candidate is shown marked `not confirmed`. The preview gains a `✓ reviewed (attempt n/3)` / `⚠ …` line and, for shadowed matches, `Stopped by an earlier layer on N of them`. The `Regenerate` option is replaced by `Amend with feedback…` (free-text amendment fed to a fresh loop together with the current candidate; empty input regenerates); `Edit value` marks the rule `edited by hand — not reviewed`. While the loop runs a waiting panel (`ui.custom`, status widget on hosts without it) shows `Attempt n/3`, the phase (generating / checking against history / reviewing) and earlier failures; Escape cancels.

- omp model roles (omp only; real pi is unchanged): the gray-zone classifier reads omp's built-in `judge` role, the second-layer classifier a custom `verdict-fallback` role and EXPLAIN-GATE a custom `explain-gate` role (assignable in `/model` → Roles). An explicit role assignment beats the matching config key (`classifierModel`, `classifierFallbackModel`, `explainGateModel`); for the classifier the order is `--auto-mode-model` flag > `PI_AUTO_MODE_MODEL` > `judge` role > `classifierModel` > session model. Only an explicit assignment counts — omp's built-in priority defaults for an unassigned `judge` never select the classifier. A `judge` assignment resolving to a non-chat model (native judgment runner, `kind: "tiny"`) cannot be called, so it is skipped with a one-time warning (config / session model is used); a kind-less model such as `typesafe/jev-latest` works. An assigned but unresolvable role falls back exactly like the config key it shadows (classifier / explain → session model, fallback → inactive) with a one-time warning. The `judge` role is shared with omp's own judgment features, so one assignment drives both. The footer reflects role-picked models. The custom roles are listed in `/model` → Roles while unassigned only if you add `modelTags` entries to `config.yml` (see `docs/configuration.md`); an extension cannot register them (importing omp's settings registry from an extension loads a second, non-functional module instance).
- **Approval modes** ([ADR-0005](docs/adr/0005-approval-modes.md)): one `mode` key replaces the master switch and `autoDeny` — `default` (deny / ask / allow), `yolo` (deny / allow, never prompts: anything that would have been an ask is blocked with an *explain or rewrite* request, block tag `yolo-retry`, and the classifier is told no human is available), `noAutoDeny` (ask / allow: every auto-review deny — floor, `deny` rules, classifier, fail-closed — becomes a confirmation prompt carrying `(noAutoDeny: this would have been denied — your call)`; non-interactive still denies) and the session-only `off` (ungated; a `mode: "off"` in a user or project config file is ignored with a warning). Classifier prompts are restricted per mode (`modeChoices`): yolo lists only `allow`/`deny`, noAutoDeny only `allow`/`ask`, default is byte-identical to before; the restriction travels to the jev adapter as an `Allowed verdicts: …` marker line and shrinks the jev `choice` question (criteria re-folded, no-human instruction in yolo, two-key probabilities print as `jev: allow 70% (confidence 65%; deny 30%)`). A yolo contract slip (`ask` from the classifier) consults `classifierFallbackModel` when configured (`enforce` applies its verdict, new `yolo-ask` trigger in the audit `fallback` object), else blocks.
- Per-mode jev probability thresholds: `defaultDenyThreshold`, `defaultAllowThreshold`, `yoloDenyThreshold`, `noAutoDenyAllowThreshold` (0–100 or `null`) re-map a non-demoted first-layer jev verdict via `applyModeThresholds` (default: deny, else allow, else ask; yolo: deny else allow; noAutoDeny: allow else ask); a re-mapped reason ends with ` — <mode> thresholds: <choice> → <mapped>`, audit records gain `mode` and (when re-mapped) `thresholdVerdict`.
- yolo protected paths: `yoloDenyPaths` and `yoloOmpDir` (`"deny"` default | `"allow"`) decide what a `denyPaths` / `.omp` gate hit does when nobody can be asked; both stay terminal asks in the other modes. A yolo deny carries no path plaintext in the block reason or notification (ADR-0002).
- Scopes: every approval key (`mode`, `confidenceThreshold`, the thresholds, `yoloDenyPaths`, `yoloOmpDir`, `classifierFallbackMode`) resolves session > trusted project > user > default; session overrides persist per session id under `<agentDir>/config/pi-verdict-sessions/<sessionId>.json` (50 newest kept). `--verdict-mode default|yolo|noAutoDeny|off` seeds the session scope; `/automode status` shows each value's source.
- `/automode` quick settings panel: a `SettingsList` with a `scope` row (session | project | user), cycling toggles for `mode` / `yoloDenyPaths` / `yoloOmpDir` / `classifierFallbackMode` and a slider (`←/→` ±5, `-`/`+` ±1, `x` off, `i` inherit) for the five percent keys; `inherit` drops the key at session/project scope. Hosts without `ui.custom` get a select/input menu.
- The quick settings panel's `mode` row shows the registered `toggleShortcut` (e.g. `mode    [ctrl+shift+y]`), starting at a fixed column inside the label cell; nothing is shown when the shortcut is disabled.
- Footer and prompt status: the leading chip shows the mode (`AUTO` / `YOLO` / `NO-AUTODENY` / `AUTO OFF · ungated`), `deny≥N%` / `allow≥N%` badges show the active mode's thresholds, yolo adds `denyPaths allow` / `.omp allow` risk chips; with `footer: "off"` a `verdict-mode` status-bar chip (`🛡 AUTO` / `🛡 YOLO` / `🛡 NO-AUTODENY` / `🛡 OFF · ungated`) mirrors the mode (with the footer on, on pi or omp, the footer itself is the only mode indicator, so there is no duplicate `AUTO`).

### Changed

- statusline wording clarified: the off state changes from hidden to always shown in dim color; the two states display `auto mode on` (highlighted) / `auto mode off` (dim)

- `/automode` command semantics clarified: a bare call is now a **read-only status display** (fixes the side effect where viewing flipped the state); `/automode on|off` is an idempotent set (no flip when equal to the current value); unknown arguments are strictly rejected with usage listed, case normalized

- `extensions/auto-mode.ts`: Auto Mode extension prototype: implements three-state verdicts (allow / ask / deny) on the `tool_call` hook as "rule layer first + model classifier for the gray area" (#3)
  - Rule layer: bash unconditional/conditional allowlist + dangerous regexes (matched against the full command string) + six levels of file path sensitivity (S0 secrets ~ S5 outside CWD)
  - Model classifier: Claude Code-style condensed `<transcript>` + `<verdict>` prefix output contract; default "introspection" (inherits the current session model), can be set via `--auto-mode-model` / `PI_AUTO_MODE_MODEL`
  - fail-closed: classifier exception/timeout (15s)/output violating the contract -> block; non-interactive mode ask -> block
  - Transparency: `/automode` toggle command, footer `🛡️ auto` status, block notifications include the verdict reason, `PI_AUTO_MODE_DEBUG=1` full verdict notifications
- `research/claude-code-classifier-prompts.md`: Claude Code permission classifier prompts reconstructed from Langfuse (hundreds of samples/24h) (#4)
- `research/cache-sim/`: offline replay of verdict-cache benefit: two-key LRU replay of historical CC classifier verdicts (1,2xx entries/2x sessions), hit rate 3.2%, 0 dangerous disagreements; basis of the #5 decision and reproducible scripts (fetch-io / simulate / kinds)
- `research/rule-engine-sim/`: rule engine benefit measurement: 746 real bash calls cross-replayed through two engines (tree-sitter AST x this layer), measured porting benefit zero, real security holes zero, the real targets are allowlist breadth and classifier cost (#6)
- `research/pi-model-call-and-ref-implementations.md`: survey of Pi extension model-call/config APIs and extraction of three open-source permission extension implementations, including a rule-layer seed set (#2)
- `CONTEXT.md`: domain glossary (Auto Mode / verdict / rule layer / gray area / classifier / introspection / fail-closed / three-state verdict / ask downgrade)
- `package.json` + `tsconfig.json`: extension type checking (`bun run typecheck`)
