# Configuration Reference

Everything the gate reads from disk lives in `<agentDir>/config/pi-verdict.json` (first run generates a template there; `PI_CODING_AGENT_DIR` overrides the location). This page is the key reference; the README keeps a quick-start subset. The normative behavior of each key is in [adjudication-rules.md](adjudication-rules.md), terms are defined in [CONTEXT.md](../CONTEXT.md).

## Keys

Defaults are the built-in values used when a key is absent. The first-run template differs from them in three places: it pre-fills `allow` (`^ls\\b`), a starter `tools` allowlist (`ask`, `todo`, `wait`, `task`, `yield`, `think`, `checkpoint`, `rewind`, `recall`, `reflect`) and a starter `denyPaths` list (`~/.ssh/`, `~/.profile`, `~/.gnupg`, `~/.mc`, `~/.zshrc`, `~/.bashrc`); existing configs are never rewritten. "Session" marks keys that may also be set in session scope (resolution `session` > `local` > `global` > default, [CF-5](adjudication-rules.md#cf-5-session-scope)); a trusted project file (`local`) replaces global values key by key, so a project list replaces the global list ([CF-4](adjudication-rules.md#cf-4-merge-semantics)). Invalid values are skipped with a warning and the default applies ([CF-6](adjudication-rules.md#cf-6-invalid-values)).

## Key notes

- `allow`/`deny` are JS regex arrays; **`deny` wins over `allow`**, both beat the classifier. Match targets: bash/powershell = the full command string; file tools = the resolved absolute path (on Windows in POSIX form: `/` separators, no drive letter — write `^/proj/`, not `^C:\\proj\\`) (`grep`/`find`/`ls` with an omitted `path` resolve to the cwd — pi's documented default); other tools (e.g. MCP) have no command or path shape to match against `allow`/`deny`, so they land in the gray zone unless named exactly in `tools` (below).
- `tools: ["ask", "propose_commit"]` is an exact tool-name allowlist for that gray-zone family (MCP/custom tools with no path or command shape, e.g. `ask`, `propose_commit`, `propose_changelog`, `todo`) — a case-sensitive exact match on the tool's registered name bypasses the classifier and returns allow directly. It does not extend to, or interact with, the built-in floor or `denyPaths` (neither covers this family either, so there is nothing to bypass there). Only tool names can be listed: `write` to an `xd://` device (omp's mounted tools) is a `write` call graded by path, not by tool name. The first-run template pre-fills a starter list of omp tools that have no side effect of their own or are gated elsewhere — `ask` (the user is the gate), `todo` (session task list), `wait` (blocks on already-started jobs), `task` (subagents are gated by this extension too), `yield` and `think` (hidden result/scratchpad tools), `checkpoint`/`rewind` (prune session context only; no file or git restore), `recall`/`reflect` (read the configured memory backend). Deliberately absent: `glob`/`ast_grep`/`lsp` (path-scoped reads that would skip `denyPaths` in this family), `web_search` (query text leaves the machine), `retain`/`learn`/`memory_edit`/`manage_skill` (persist content into future prompts), `eval`/`github`/`debug`/`ida`/`security_scan`/`ast_edit` (execute code or mutate state). It is a pre-filled *user declaration*, not a built-in: edit or empty it freely; existing configs are never rewritten, so add the names by hand (or via `/verdict`) to adopt it. An empty list leaves the family entirely classifier-routed.
- `denyPaths` are plain paths (not regexes) you declare **protected**: any tool call touching them — file tools via their path (scope tools via their whole search scope: omitted path/cwd, or a parent directory of a declaration), bash via path tokens extracted from the command string — triggers a **terminal ask** you adjudicate (non-interactive sessions degrade to deny). Not affected by `builtinDenyFloor: false`. The first-run template pre-fills a starter list (`~/.ssh/`, `~/.gnupg`, `~/.mc`, shell rc/profile files), active from the first session after the initial run — a pre-filled user declaration you can edit or empty; existing configs are never rewritten.
  The classifier only ever learns that protected paths *exist*; the paths themselves never leave your machine, and a matched path shows **only** in the local confirm dialog.
- `builtinDenyFloor: false` is the master switch of the built-in rules: every built-in danger rule and path tier acts as `allow` (no judgment — the call goes to the classifier; risk accepted by you; the classifier, your rules and custom danger rules remain).
- `dangerRules` configures the bash danger rules by id. `{"sudo": "ask"}` changes a built-in's action (`deny` default, `ask` asks you — a deny headless or in `yolo` — and `allow` passes no judgment so the call goes to the classifier); `{"git-restore": false}` removes it; `{"npm-publish": {"pattern": "\\bnpm\\s+publish\\b", "action": "ask", "reason": "publishing"}}` adds a custom rule (action default `deny`, reason default `custom danger rule`, pattern compiled case-insensitively unless `flags` says otherwise, `g`/`y` rejected). Built-in ids: `rm-recursive`, `rm-root`, `sudo`, `chmod-777`, `raw-device`, `git-push-force`, `git-reset-hard`, `git-clean-force`, `git-checkout-dot`, `git-restore`, `remote-exec`, `gh-repo`, `gh-release`, `fork-bomb`. Project and session scopes merge per id over global; an invalid entry is skipped with a warning. When several rules match, the strongest action wins and the reason lists every hit (`rule <id>: <reason>`). A user `deny` regex is evaluated before them and a user `allow` regex beats a built-in `ask` but never a built-in `deny`; only a permission grant naming the rule id (`verdict_grant` `rules`) lifts a built-in deny ([GR-5](adjudication-rules.md#gr-5-coverage-check)).
- `pathRules` configures the built-in path tiers: `s0-secret` (default `deny`), `s1-system-read` (`allow`, i.e. gray), `s1-system-write` (`deny`), `s2-user-rc-write` (`allow`) and `s3-git-meta-write` (`deny`) each take `deny`, `ask` or `allow`. Block and ask reasons are prefixed `tier <id>:`, which a permission grant's path entry can cover; a tier ask never offers Explain.
- `gateOmpDir: true` (default) is the **forced `.omp` gate**: any file-tool path or bash command touching a `.omp` directory — a `.omp` path segment (case-insensitive) on the lexical or symlink-resolved form, or `.omp` as a bare word in a bash command (`cd .omp`) — triggers a **terminal ask** you adjudicate (non-interactive sessions degrade to deny). Pipeline position: after the built-in floor and your `deny` regexes, before `denyPaths` and `allow` — an `allow` regex cannot skip it. The ask reason returned to the agent carries no path; the matched form shows only in the local confirm dialog. `grep`/`find`/`ls` are checked on their own target (omitted path = cwd) only: a recursive search that merely traverses a nested `.omp` is not an access. Lookalikes (`.ompx`, `x.omp`, `.omp.bak`) do not match; bash matching is token-level like `denyPaths` (substitution/base64/script-content spellings fall through to the classifier). `false` disables it; `/verdict` toggles it too (a project file can also unset it to inherit the global value).
- `footer` (default `"full"`): style of the footer status. `"full"` renders Nerd Font powerline blocks — approval mode chip (`AUTO` / `YOLO` / `NO-AUTODENY` / `AUTO OFF · ungated`), risky settings (`floor off`, `.omp gate off`, in yolo `denyPaths allow` / `.omp allow`), the classifier model (`↺` = inherited session model, `⚠ ↺` = configured model unavailable so the session model is used, `↳ <id>·shadow|enforce` = fallback model), per-session verdict counters (allow / ask / deny: final pipeline verdicts of root-session calls, reset at session start) and info badges (`≥N%` for `confidenceThreshold`, `deny≥N%` / `allow≥N%` for the active mode's thresholds, `subagent normal|auto`). `"compact"` is one plain text line with the same content minus counters; `"off"` clears the status. Hosts whose theme lacks `bg`/`getBgAnsi` render compact. The footer never shows command or path text ([PP-6](adjudication-rules.md#pp-6-plaintext-confinement)). Editable from `/verdict`; an invalid value warns and falls back to `"full"`.
- `modeStatus` (default `true`): approval-mode chip (`🛡 AUTO` / `🛡 YOLO` / `🛡 NO-AUTODENY` / `🛡 OFF · ungated`) in the prompt status bar, published with `ctx.ui.setStatus("verdict-mode", …)`. On omp the text renders inside the status line's `status` segment (or as trailing facts when `status` is not in your segment list and omp's `statusLine.showHookStatus` is on); omp strips ANSI, so the chip is plain text. On pi it is hidden while the footer is on (the footer's lead chip already shows the mode) and shown with `footer: "off"`. `false` removes the chip everywhere (with `footer: "off"` that leaves no mode indicator). Session-scopable like `gateOmpDir` / `footer` and editable from `/verdict` (`mode in status bar`); a non-boolean value warns and counts as `true`.
- `grantStatus` (default `true`; session > local > global): while permission grants are active ([GR-6](adjudication-rules.md#gr-6-lifetime-revocation-and-visibility)) the prompt status bar shows an extra `🔑 N` entry (status key `verdict-grants`, plain text on omp). The footer's own grant count (`\uF084 N` in the `full` style, `🔑 N` in `compact`) is controlled by `footer` and appears only while grants exist; `grantStatus: false` hides the status-bar entry only. With the footer on pi the footer sits in the same bar, so the entry is hidden there as with the mode chip. Grants themselves are stored in the session file (`grants`, [CF-5](adjudication-rules.md#cf-5-session-scope)), never in a config file; manage them with `/grants`.
- `mode: "default" | "yolo" | "noAutoDeny"` (default `"default"`) is the **approval mode** ([MD-1](adjudication-rules.md#md-1-modes-and-verdict-sets)); it replaces the old master switch and `autoDeny` key.
  - `default` — deny / ask / allow (the original behavior).
  - `yolo` — deny / allow; **never prompts**. Anything that would have been an ask (classifier `ask`, demotion by `confidenceThreshold`, failed fallback, contract slip) becomes a block carrying an *explain or rewrite* request (block tag `yolo-retry`) so the agent can justify the action or retry with a narrower command. The classifier prompt lists only `allow`/`deny` and says no human is available; the jev question is restricted to those two choices (an `Allowed verdicts:` marker line in the system prompt). The built-in floor and your `deny` rules still deny. `denyPaths` and `.omp` gate hits follow `yoloDenyPaths` / `yoloOmpDir`.
  - `noAutoDeny` — ask / allow: every auto-review deny (built-in rule deny, your `deny` regexes, classifier deny, classifier fail-closed) becomes a confirmation prompt showing the would-be deny reason. Non-interactive sessions still deny. The classifier is restricted to `allow`/`ask`.
  - `off` — ungated; **session-only**: set with `/automode off`, `--verdict-mode off` or the shortcut cycle. A `mode: "off"` in a user/project file is ignored with a warning, so a config file or a cloned repository can never ungate the session.
- `yoloDenyPaths` / `yoloOmpDir` (`"deny"` default | `"allow"`) are yolo-only: what a `denyPaths` hit / a `.omp` gate hit does when nobody can be asked. `deny` blocks with `[auto-mode protected-path block]`, `allow` passes silently; neither the notification nor the block reason carries path plaintext ([PP-6](adjudication-rules.md#pp-6-plaintext-confinement)). Default and noAutoDeny keep the terminal ask.
- `defaultDenyThreshold`, `defaultAllowThreshold`, `yoloDenyThreshold`, `noAutoDenyAllowThreshold` (0–100 or `null`, default `null`) are per-mode **jev probability thresholds**, applied to a non-demoted first-layer jev verdict (LLM classifiers and fallback verdicts are never re-mapped): default mode → `deny` if jev's deny probability ≥ `defaultDenyThreshold`, else `allow` if allow probability ≥ `defaultAllowThreshold`, else `ask`; yolo → `deny` if deny probability ≥ `yoloDenyThreshold`, else `allow`; noAutoDeny → `allow` if allow probability ≥ `noAutoDenyAllowThreshold`, else `ask`. An unset (`null`) threshold of an otherwise active mode falls back to jev's own choice for that verdict; with all of a mode's thresholds `null` nothing is re-mapped. A re-mapped reason ends with ` — <mode> thresholds: <choice> → <mapped>`, and the audit record carries `thresholdVerdict` (plus `mode` on every record).
- **Scopes**: every approval key (`mode`, `confidenceThreshold`, the four thresholds, `yoloDenyPaths`, `yoloOmpDir`, `classifierFallbackMode`) plus the `gateOmpDir`, `footer` and `modeStatus` switches resolves **session > local > global > default** (`local` = the trusted project config, below; `global` = the user config). Session scope is written by `/automode …`, the shortcut, the `--verdict-mode` flag, the `/automode` panel and the `/verdict` menu to `<agentDir>/config/pi-verdict-sessions/<sessionId>.json` (the 50 newest files are kept; an unreadable file warns and is ignored; forks and new sessions start without it; a session `gateOmpDir` / `footer` / `modeStatus` with an invalid value is skipped with a warning, so the `.omp` gate stays on). `/automode status` prints each value's source.
- **`/automode` panel**: bare `/automode` with a UI opens the approval settings menu at session scope. The scope badge in the top-right of the title border (`⟨ session ⟩`) cycles global → local → session with `Tab` (`⟨ local · untrusted ⟩` when the project config is not trusted — edits are saved but not applied). `↑/↓` move, `←/→` change the selected row (`‹ value ›`), `enter` steps to the next value, `a` toggles between the effective mode's settings and every mode's. Percent rows step ±5 with `←/→` (`-`/`+` ±1, `x` off, `i` inherit; left of `0%` is `off`, then `inherit`); a 10-cell bar shows the value. Rows are grouped in sections (`all modes`, `default`, `yolo`, `noAutoDeny`); with the effective mode `off` only the mode row is shown until `a`. `inherit` drops the key at session/local scope; `off` for `mode` exists at session scope only. The line under the selected row explains the value, the effective value and its source, and warns when a higher-precedence scope overrides the edited one. Every change is written immediately. Hosts without `ui.custom` get a notification pointing at `/automode status|default|yolo|noautodeny|off`.
- `classifierModel: "provider/model-id"` sets the classifier model (e.g. a fast flash-class model); precedence is flag > env > config > session model (self-reflection); an invalid value falls back to the session model with a one-time warning.
- The spec accepts pi's native `--model` thinking suffix: `"zai/glm-5.3-flash:low"` sets classifier thinking to effort low (default without suffix: thinking explicitly off).
- `explainGateModel: "provider/model-id[:thinking]"` and `explainGatePrompt: "…"` configure the **EXPLAIN-GATE role**, a human-invoked model call behind the ask dialog's **Explain…** option. `explainGateModel` defaults to the session model (an unavailable value falls back to it with a one-time warning; thinking defaults to off); `explainGatePrompt` replaces the built-in default task (`Explain what this action does and why the gate held it for confirmation.`) used when the question is left empty — a typed question replaces the task instead. The call (one attempt, 30 s timeout) carries the sanitized transcript, the full code under review and the gate's stated reason under a fixed system prompt. Its answer is advisory text rendered in the dialog only: it never reaches the agent, the verdict, the audit log or the classifier. Protected-path asks (`denyPaths` hits and the `.omp` gate) never offer **Explain…** — their path plaintext is UI-only ([PP-6](adjudication-rules.md#pp-6-plaintext-confinement)). The dialog's **No** row is an inline text field while highlighted (`→ No, <text>`), available for every ask: Enter with text declines and forwards the text to the agent in the block reason, Enter with empty text (or Escape) declines plainly. Both keys are per-project overridable like the rest; RPC mode and hosts without `ui.custom` get the plain Yes/No confirm.
- `classifierModel: "typesafe/jev-latest"` opts into the bundled **jev decisions adapter** (`extensions/jev-adapter.ts`, loaded with the package; disable it individually with `pi config`). Gray-zone verdicts become one `choice` question against TypeSafe's jev decisions API; the typed answer is synthesized into the usual `<verdict>` text with probabilities and confidence, so timeouts and fail-closed semantics are unchanged. Two transports (`PI_VERDICT_JEV_TRANSPORT`, default `openrouter`): **OpenRouter** sends to `POST /api/alpha/decisions` (an alpha API) and reuses pi's OpenRouter login (`/login openrouter`) with `OPENROUTER_API_KEY` as fallback — no separate typesafe account; **typesafe** sends to TypeSafe's official `POST api.typesafe.ai/v1/systemone` with `TYPESAFE_API_KEY` (self-service at console.typesafe.ai — pi has no typesafe login, so this is that transport's only credential source). The two wire contracts are isomorphic except for the model slug; the TypeSafe API does not report per-call cost (it shows as $0). `PI_VERDICT_JEV_URL` overrides whichever transport is active. Thinking suffixes are meaningless for jev and are ignored. Caveats ([JV-3](adjudication-rules.md#jv-3-translation)): the denyPaths existence hint does not reach jev (denyPaths themselves stay rule-enforced before the classifier); jev treats the transcript as data and "does not treat it as hostile by default" (TypeSafe docs), so adversarial transcript content can move its judgment; omp hosts cannot load the adapter and the setting falls back there.
- `toggleShortcut` rebinds the key that **cycles the session approval mode** (`default → yolo → noAutoDeny → off → default`, silent, session scope; `null` or empty disables it, not persisted).
- `audit: true` turns on the **verdict audit log** (#54): every gray-zone adjudication appends one self-contained JSONL record to `<agentDir>/verdicts/<sessionId>.jsonl` — timestamp, session id, cwd, model id, tool name + input, action line, thinking level, the full transcript sent, the raw response text, the parsed verdict + reason, source (`model`/`fail-closed`/`protected-path`), shadow-cache probe result, and the degraded flag. Rule-layer allow/deny decisions are never recorded; **protected-path asks are recorded** (#62) — their confirms are user adjudications that grade the denyPaths rules (the record carries the matched path in `detail`). Interactive asks (classifier and protected-path alike) record **ground truth** (#62): the record is written after the confirm resolves, carrying `userAnswer` (`allowed`/`declined`) and `answeredAt` (`ts` stays adjudication time); a non-interactive degraded ask records immediately as its effective deny, without the answer fields. Accepted trade-off of the deferred write: closing pi while a confirm dialog is open loses that ask record (one record per verdict, append-only — no pre-write/rewrite). Records of triggered calls carry an optional `fallback` sub-object when the second layer is configured (#63 — see above for its reading discipline). Retention keeps the 20 most recent session files (pruned at session start). Full fidelity by design: records may contain protected-path plaintext — that stays inside your machine ([AU-1](adjudication-rules.md#au-1-audit-scope)); the directory carries no special protection and reads/writes to it are graded like any other path (records can contain untrusted raw model output, including fail-closed failures — treat the directory as sensitive if you read it back). The sink is fail-soft: a write failure never affects or delays a verdict — one warning, then silent for the rest of the session. Never an adjudication input: append-only, never read back into gate decisions (shadow-cache discipline). `/automode` shows `audit: on → <path>` while active. Off by default; no `verdicts/` directory is created unless a recordable adjudication happens with audit on.
- `notifyAllows: true` surfaces every **classifier allow** as an info notification (verdict reason + action line) — the gate's judgment calls become visible, e.g. jev's probability breakdown (`jev: allow 66% (confidence 49%; ask 33%, deny 1%)`). Default `false`: notifications stay limited to what needs your attention (deny/ask/warnings) and passes stay silent. Mechanical passes never notify under this option — allow-rule hits are echoes of your own declarations, and a protected-path confirm's visibility is the dialog itself; complete records live in the verdict audit log instead. Orthogonal to the debug switch: shadow-cache annotations stay debug-only, and with both on the classifier-allow notification appears exactly once (with the shadow suffix). Config-only, new-session semantics.
- `confidenceThreshold: 0–100` (formerly `classifierMinConfidence`, now ignored with a warning) sets the **confidence floor** — the minimum confidence at which the first layer may adjudicate on its own ([CS-1](adjudication-rules.md#cs-1-confidence-floor), #67). A jev verdict with confidence strictly below the floor is **demoted**: the call cascades to the second layer if `classifierFallbackModel` is configured, otherwise it is asked of you directly (non-interactive degrades to deny; any verdict — allow, ask, deny — demotes). At or above the floor the first layer is fully autonomous and nothing extra runs. The floor works standalone — it does not require a second layer. The rendered confidence floors rather than rounds (a true 49.6% renders 49% and cannot slip past a 50 floor), and jev's confidence is hard-required by the adapter (contract drift fails closed). LLM first layers emit no numeric confidence: the floor (and the whole cascade) is inert for them. `null` (the default) = off; invalid values skip into the one-shot warning channel. The old key name `classifierFallbackConfidence` (0.10.0) warns as renamed and is ignored.
- `classifierFallbackModel: "provider/model-id"` adds an opt-in **second-layer classifier** consulted on exactly three occasions ([CS-3](adjudication-rules.md#cs-3-cascade-triggers)): a **demotion** (confidence below `confidenceThreshold`), a **fail-closed** first layer, and a **yolo-ask slip** (a first-layer ask in `yolo` mode, where nobody can be asked). It gets its own 15s-per-attempt budget (the two-tier retry can double it, mirroring the first layer's per-attempt 25s) and, unlike jev, receives the denyPaths existence hint. The cascade is active only while this key is set; the model is the omp `verdict-fallback` role when assigned, else this key, and it never falls back to the session model; an unresolvable model warns once per session. High-confidence asks do not consult it — a confident ask goes straight to you.
- **omp model roles** (omp only): the three model selections also exist as omp model roles, assignable in `/model` → Roles — `judge` (omp's built-in role; gray-zone classifier), `verdict-fallback` (second-layer classifier) and `explain-gate` (EXPLAIN-GATE). An explicit role assignment wins over the matching config key (`classifierModel`, `classifierFallbackModel`, `explainGateModel`), including its thinking suffix (`provider/id:low`); the `--auto-mode-model` flag and `PI_AUTO_MODE_MODEL` still win over `judge`. An unassigned role changes nothing (omp's built-in priority defaults for `judge` are ignored). Role models must be chat-kind: a `judge` assignment resolving to a native judgment runner or `tiny` model is skipped with a one-time warning; `typesafe/jev-latest` (no `kind`) works. `judge` is shared with omp's own judgment features, so one assignment drives both. omp lists a custom role in `/model` → Roles only once it is assigned or has a tag; to see `verdict-fallback` / `explain-gate` while unassigned, add to omp's `config.yml`: `modelTags: { verdict-fallback: { name: "VERDICT FALLBACK" }, explain-gate: { name: "EXPLAIN GATE" } }`. Roles assigned in `config.yml` (`modelRoles:`) resolve either way. Real pi has no roles and keeps the config keys only.
- **Listing the custom roles in `/model` → Roles** (omp only): omp shows a custom role only once it is assigned or has a `modelTags` entry in omp's `config.yml`. In `/verdict` the `custom roles` row (global scope only) switches the entries `verdict-fallback` ("VERDICT FALLBACK") and `explain-gate` ("EXPLAIN GATE") on or off: `←/→` marks the new value as pending (shown in the warning color, with what will be written), `enter` applies it, moving away or `Esc` drops it. Other keys and tags are preserved, but the file is re-serialized, so YAML comments are lost. An unreadable `config.yml` shows the row as `unreadable` and notifies the error. `judge` is a built-in omp role and needs no tag.
- `classifierFallbackMode: "shadow"` (default) — the second layer **records its opinion** (audit `fallback` sub-object + `/automode` counters: `triggered · agreed · would-overrule · errored`) and never changes any verdict: a demoted call is asked of you, a fail-closed deny stands. `"enforce"` — the second layer **adjudicates de novo**, with exactly one carve-out: a demoted first-layer **deny** that the second layer would allow is asked of you instead (never an automatic allow; headless degrades to deny). A failed or unresolvable fallback on a cascaded call falls to you as well — the tier that was to adjudicate is down (headless → deny, one-time warning). Audit reading: the top level keeps **first-layer semantics** (records of non-interactive asks — native, demoted, escalated — carry their effective deny, per the standing convention), `demoted: true` marks floor fires, and the applied verdict lives in `fallback.effective` (enforce rows, failure rows carry the `"ask"` you got). Shadow→enforce flip is a human decision after shadow data ([CS-6](adjudication-rules.md#cs-6-shadow-mode)); config-only, new-session semantics.
- `subagentGate: "off" | "normal" | "auto"` (omp only, default `"off"`) controls the `ask`s raised inside **subagents**. omp creates subagent sessions in-process with no UI, so without this key every subagent ask would degrade to deny. `"normal"`: the confirmation dialog appears on the **root** session's UI (titles and notifications carry a `[subagent <id> (<name>)]` label); if nobody answers within `subagentAskTimeoutMs`, or the root has no UI (e.g. `omp -p`), the ask is resolved without a human. `"auto"`: never prompt; always resolve without a human. `"off"` (default): the gate is inert in subagents — no rule, floor or classifier check runs on their tool calls; set `"normal"` or `"auto"` to gate them. pi has no subagent identity (`ctx.agent`), so pi behavior is unchanged.
  **Resolving without a human** consults `classifierFallbackModel` once, only when the ask came from the classifier (its `ask`, or a demoted/shadowed cascade outcome the second layer allowed, which then applies directly). Only an explicit `allow` permits the call; a deny, ask, error, timeout or an unconfigured/unresolvable second model denies (block tag `subagent-auto`). Asks that did not come from the classifier — protected-path and `.omp` gate asks, and rule/fail-closed/classifier-deny asks that exist only because `mode: "noAutoDeny"` — always deny, with no path plaintext in notifications or the block reason ([PP-6](adjudication-rules.md#pp-6-plaintext-confinement)). A demoted first-layer deny is never auto-allowed ([CS-7](adjudication-rules.md#cs-7-enforce-mode)). Subagent notifications are shown on the root UI with the label. A cancelled subagent run closes its pending root dialog and blocks with `subagent-cancelled`; the second model is not consulted.
- `subagentAskTimeoutMs` (positive integer, default `60000`) is the `"normal"`-mode deadline for the root dialog, measured from enqueue — time spent queued behind another dialog counts. Root dialogs are serialized, so concurrent subagent asks are shown one at a time. **Set omp's `extensionHandlers.toolCallTimeoutMs` (in `config.yml`, default 30000) to at least `subagentAskTimeoutMs + 60000`**: omp pauses a handler's active-work budget only for the session's own dialogs, so a subagent waiting on the root UI keeps spending it, and an expired budget blocks the call (`Extension … timed out`). With `audit: true`, subagent asks record `subagent: { id, name, resolution }` (`human` / `timeout` / `auto`) and second-model resolutions record `fallback.triggeredBy: "subagent-ask"`.
- `rules: ["…"]` are free-text classification rules appended to every classifier prompt (LLM classifiers and the jev adapter, where they extend the verdict question's instructions). Where a rule applies, it takes precedence over the classifier's default criteria. Non-string or empty entries are skipped with a warning.
- **Project config**: when a session's cwd (or an ancestor) contains `.pi/pi-verdict.json` (`.omp/pi-verdict.json` on omp — the dot-dir matches whichever host tree this config lives in), the gate can load it. The nearest file walking up from cwd wins; the walk stops before your home dir and before the agent tree's own root. It is shallow-merged over the global config for that session — every key except `toggleShortcut` (never per-project overridable) and `_hint` (a project `mode: "off"` is ignored — `off` is session-only). **A project config is applied only when its project is trusted; an untrusted or undecided project config is never applied**, because a repository you clone could otherwise weaken the gate (e.g. `allow`, `builtinDenyFloor: false`, `mode`). When an interactive session starts in a project with a config and no recorded decision, the gate asks: **Trust** (apply it and remember), **Not now** (ignore it this session; asked again next session), or **Never** (ignore it and don't ask again). Decisions are stored per project root (the directory containing the dot-dir; exact match, not subtrees) in `<agentDir>/config/pi-verdict-trust.json`, shaped `{ "trusted": ["/abs/root", …], "untrusted": ["/abs/root", …] }`. Edit it by hand to revoke trust or to be asked again; a malformed trust file is reported and never overwritten. Trust is per root, not per file content: editing a trusted project's config does not re-prompt. Headless sessions and subagents never prompt: an undecided project config is ignored (a subagent follows the decision already stored by the main session).
- **`/verdict` menu**: `/verdict [global|local|session]` (default `global`; an unknown argument prints the usage) opens the rules menu. `Tab` cycles the scope badge (global → local → session). The main page lists the five list keys (`allow`, `deny`, `tools`, `denyPaths`, `classifier rules` = `rules`) with their entry counts (`not set` at local scope when the project does not override it), the `.omp gate`, `footer` and `mode in status bar` switches (`←/→` change them; `inherit` drops the key at local/session scope), and on omp the `custom roles` row. `enter` opens a list page: `+ add` types a new entry inline, `enter` on an entry edits it inline (`enter` saves, `esc` cancels; multi-line classifier rules can only be removed), `d` twice removes it, `←`/`esc` goes back. Global edits rewrite only the edited key of the global file (other keys, order and `_hint` kept). **Local** replaces the global list for the project: the first local add copies the global list and appends the entry (a notification says so), and `× unset` (confirmed with a second `enter`) drops the override. **Session** additions are stored as `ruleAdditions` in the per-session overrides file and appended to the local/global list for this session; inherited entries are shown dimmed with their source and skipped by the cursor. The session reloads the rules right after each save. Editing a project file never trusts it — an untrusted project's edits are saved but not applied (the badge says `local · untrusted`). A file that is not valid JSON is refused with a message; a list key that is not an array, or a `gateOmpDir` / `footer` / `modeStatus` with an invalid value, is shown as `invalid` and locked — fix it by hand. Without `ui.custom` the command prints a notification and does nothing.
- **`/rule` generator**: `/rule <description>` asks the session model (thinking off; sees the recent user messages and tool calls, never your `denyPaths`) for one rule of kind `allow`, `deny`, `denyPaths`, `tools` or `rules`. The candidate then goes through a bounded loop (3 attempts, each failure fed back to the model): parse and validation errors, then — for `allow` / `tools` — a replay of the matching recent calls through the rule layers (a rule that the built-in floor, user `deny`, the `.omp` gate or `denyPaths` would still stop for every match can never take effect and is rejected), then one critic call to the same model (`ok` / `revise`). A rule matching no recent call is accepted with a warning. If the critic is unavailable the rule is shown as `review unavailable`; after three failed attempts the last candidate is shown as `not confirmed`. A waiting panel shows the attempt, phase and earlier failures; Escape cancels. The preview lists the last-50-tool-call matches (regex, `denyPaths`, `tools`; free-text `rules` are not checked), which of them an earlier layer still stops, and offers `Save — session only` / project / global, `Edit value`, `Amend with feedback…` (empty feedback regenerates), `Cancel`. Project and global saves write the same keys `/verdict` edits (a first project add offers a copy of the global list). Session saves go to the per-session overrides file (`<agentDir>/config/pi-verdict-sessions/<sessionId>.json`, key `ruleAdditions`, e.g. `{"ruleAdditions": {"deny": ["^git push\\b"]}}`) and are **appended** to the effective merged list at each rules reload; they live only for that session (restored on resume, pruned with old session files) and there is no session-rule removal UI. Needs an interactive UI and a session model.
- **Agent settings tool (`verdict_settings`)**: an agent-callable tool, registered on pi and omp, that reads these settings and proposes changes. `action` is `get` (effective value, its source and the stored value per scope; no approval; works without a UI), `set` (replace a key's whole value, validated like the config loader), `unset` (drop a key at one scope) or `add` / `remove` (one entry of `allow`, `deny`, `denyPaths`, `tools` or `rules`). Every key except `_hint` can be changed; `scope` is `global` (user config), `local` (project config, applied only when the project is trusted — otherwise saved but inactive) or `session` (this session only, highest precedence). Session scope takes the approval keys, `gateOmpDir`, `footer`, `modeStatus` and `rootRule`; on list keys it appends to the effective list. `toggleShortcut` is global only, `mode: "off"` is session only, and a first `local` list change starts from a copy of the global list. **Every change opens a confirmation dialog** (scope and file, key, action, stored value before and after, the agent's `reason`) in every approval mode, including `yolo`; nothing is written without your approval, and a decline is reported to the agent as a normal result. The gate itself allows calls to this tool at the rule layer ([RL-8](adjudication-rules.md#rl-8-settings-tool)) — no classifier call and no second prompt. `get` reduces `denyPaths` to a count and a change never reveals whether a `denyPaths` entry already exists, so protected paths stay out of the agent's context ([PP-6](adjudication-rules.md#pp-6-plaintext-confinement); the dialog shows them to you). Calls from subagents are refused, and so are changes when no UI is available ([ST-1](adjudication-rules.md#st-1-actions-and-keys) to [ST-5](adjudication-rules.md#st-5-writes)).
- **Ask dialog and verdict label**: the ask dialog always shows the tool call's code (bash command, write content, edit blocks); code over 40 lines / 4000 chars / 3 edit blocks is truncated and `ctrl+o` expands or collapses it inside the dialog (on a host exposing `getToolsExpanded`/`setToolsExpanded` the dialog follows the host's tool expansion, which is restored on close). The `verdict` widget row shows `awaiting your approval` while it waits, and every allowed call that did not pass by one of your own rules gets a one-line label row after its block (`<shield> bash <icon> classifier`, plus a probability bar and `allow 92%` for jev verdicts) so you can see how it passed; rule allows are recorded but not rendered. On omp the label is an aside message the agent also sees; on pi it is TUI-only. It never contains the reason or any path ([PR-4](adjudication-rules.md#pr-4-ask-dialog), [PR-6](adjudication-rules.md#pr-6-status-widget), [PR-7](adjudication-rules.md#pr-7-verdict-label)). In the interactive TUI a jev ask additionally shows an allow/ask/deny probability bar, a confidence bar against the `confidenceThreshold` floor and a `concern:` line; other hosts and RPC mode fall back to the plain-text confirm.
- **Remembered approval** ([PR-9](adjudication-rules.md#pr-9-remembered-approval)): every ask dialog except the permission-grant dialog has a second row, "Yes, and don't ask again this session". The Yes is kept in memory for the exact call (ask origin, tool name, input, cwd); the identical call then passes right after the rule layer — no classifier call, no dialog — in every approval mode, a rule-layer deny only in `noAutoDeny`. The footer shows the count (`👤 n`); `/automode forget` or the panel's `forget remembered approvals` row (`f`) clears it; a new session starts empty. Remembered allows are not audited, and the plain confirm fallback cannot remember.

## Why no built-in command allowlist?

Bypass testing of the rule layer ([writeup](../research/rule-layer-security-audit.md)) showed that allowlist robustness is very limited: command strings are obfuscatable and a sound allow claim needs shell-AST analysis a measured rule engine did not pay for ([rule-engine-sim](../research/rule-engine-sim/README.md)). The built-in layer therefore makes only **deny** claims for commands (the sound direction); command allow claims are yours. Path grading is the one built-in allow: reads outside the S0 and S1 grades and writes inside the working directory outside S0–S3 pass mechanically ([PG-4](adjudication-rules.md#pg-4-reads), [PG-5](adjudication-rules.md#pg-5-writes), [RL-5](adjudication-rules.md#rl-5-danger-rules)).

## Host notes (pi and oh-my-pi)

pi-verdict runs on both [pi](https://github.com/badlogic/pi-mono) and [oh-my-pi](https://github.com/can1357/oh-my-pi) (omp); the extension self-anchors to whichever agent tree it is installed in. On a dual-install machine the gate follows the extension copy's own location — the mere presence of `~/.omp` never redirects a pi run (and vice versa).

Implementation details worth knowing if you hack on the extension:

- omp 18's `ModelRegistry` has no `complete` method, so the classifier resolves completion through the pi-ai compat module at first gray-zone verdict (`@earendil-works/pi-ai/compat`, which omp's legacy compat layer rewrites to its bundled pi-ai). Resolution or call failures follow the usual fail-closed deny.
- Thinking control is sent in both hosts' native dialects (`thinkingEnabled`/`effort` for pi, `reasoning`/`disableReasoning` for omp); each host reads its own fields and ignores the other's.
- omp installs npm plugins under `plugins/node_modules/<pkg>/` in its config root — under `<agentDir>/` up to omp 18.0, a sibling of `agent/` since omp 18.1. The user-rules config always lives under `<agentDir>/config/` on both layouts.
